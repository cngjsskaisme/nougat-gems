## 1. Core Conclusion

The current design documents contain **4 different open/display flows** rather than a single "popup" concept.

| Flow | Trigger | State/Display Controller | Representative Example |
|------|---------|--------------------------|------------------------|
| A. Chat Widget Open | User click / External entry | `useChatState` (`desktopOpen` / `mobileOpen`) | Resume Chat Module |
| B. Registered Link Open | UI Action (`openRegisteredLink`) | `Action Dispatcher` → `Link Registry` | LLM UI inquiry card |
| C. Product Detail Open | UI Action (`openProductDetail`) | `Action Dispatcher` → Navigation Handler | NDJSON-json-render product button |
| D. Conditional UI Exposure | Spec state change | `VisibilityProvider` (`visible`) | json-render based generated UI |

These 4 flows commonly follow the principle of **"UI Components do not open directly, but go through State or a Dispatcher."**

---

## 2. Common Architecture

```text
User event (click, entry, state change)
        ↓
[In some cases] UI Component only Emits an Event
        ↓
State Layer or Action Dispatcher
        ↓
Validation (Registry, Allowlist, State Machine Guard)
        ↓
Actual open/render execution (Router, window.open, conditional rendering)
```

### Common Principles

- UI Components do not directly make API calls, directly change State, or directly select Action Handlers.
- Only pre-registered values (ID, URL, Component) are used as open targets.
- Arbitrary strings are not used as function names, Import paths, or URLs.
- Loading and Error of asynchronous Actions are managed within the UI Part scope.

## 3. Detailed Structure by Flow

### A. Chat Widget Open/Close

This is the structure defined in `이력서 채팅 모듈.md`.

#### State

```text
useChatState
├── messages
├── loading
├── desktopOpen   ← Desktop chat widget/popup display state
├── mobileOpen    ← Mobile chat widget/popup display state
├── draft
└── inquiryState
```

#### Flow

```text
[Desktop]
User click (FAB / toggle button)
        ↓
useChatState.desktopOpen = !desktopOpen
        ↓
DesktopChat Component conditional rendering
        ↓
Chat popup/widget display

[Mobile]
User click
        ↓
useChatState.mobileOpen = !mobileOpen
        ↓
MobileChat Component conditional rendering
        ↓
Full-screen/bottom sheet form chat UI display
```

#### Characteristics

- No separate `Dialog`/`Modal` component is mentioned.
- `desktopOpen` / `mobileOpen` are managed as in-memory `Application State`.
- It resets on refresh.
- Separate states per viewport allow applying responsive open policies.

---

### B. Registered Link Open

This is a flow centered around the `openRegisteredLink` Action.

#### Where It Appears

- `자체개발 - LLM UI FE.md` / `자체개발 - LLM UI BE.md`
- One of the Actions registered in the `Action Registry`

#### Flow

```text
User click
        ↓
UI Component emits action Event
        ↓
Response Renderer receives → forwards to Action Dispatcher
        ↓
Look up openRegisteredLink Handler in Action Registry
        ↓
Payload validation
        ↓
Look up Link ID → actual URL in Link Registry
        ↓
Security validation
        ↓
window.open or route navigation
```

#### Security Validation Items

- Whether it is a registered Link ID
- Whether it is an allowed Protocol
- Whether it is an allowed Host
- Whether it is a relative path or absolute path
- New window policy
- Whether `noopener` and `noreferrer` are applied

#### Blocked Items

- `javascript:` scheme
- `data:` scheme
- Arbitrary iframes
- Unregistered Domains
- Unvalidated URLs generated by LLM

#### Core Principle

> The LLM or Backend passes a Link ID instead of a URL. The Frontend looks up the actual URL from the Link Registry.

### C. Product Detail Open

This is a flow centered around the `openProductDetail` Action.

#### Where It Appears

- `Mixed-01-02 - NDJSON_json-render_접합_FE_프로그램_설계서.md` #18 Action connection

#### Spec Example

```json
{
  "type": "Button",
  "props": {
    "label": "View Details"
  },
  "on": {
    "click": [
      {
        "action": "openProductDetail",
        "params": {
          "productId": "p-01"
        }
      }
    ]
  }
}
```

#### Flow

```text
User clicks Button
        ↓
click Event occurs in UI Part based on content.ui.patch
        ↓
Renderer forwards Action Event to Action Dispatcher
        ↓
Look up openProductDetail Handler in Action Registry
        ↓
Payload validation (productId existence, etc.)
        ↓
Page navigation or popup open within Navigation URL Allowlist
```

#### Frontend Principles

- Only Actions registered in Catalog/Registry are executed
- Parameter Schema re-validation
- Arbitrary Function String execution prohibited
- Navigation URL Allowlist
- Loading and Error of asynchronous Actions are managed within UI Part scope
- Actions requiring server permissions are re-validated on the server
- Visibility is not used as a permission validation method

### D. Conditional UI Exposure (Visibility)

This is an indirect popup/display flow utilizing the `visible` attribute of the `json-render` Spec.

#### Where It Appears

- `Origin-02 - 잠재표준 - LLM UI FE.md` #5.2 VisibilityProvider
- `Mixed-01-02 - NDJSON_json-render_접합_FE_프로그램_설계서.md` UI Patch processing flow

#### Spec Example

```json
{
  "type": "Dialog",
  "props": { "title": "Confirm" },
  "visible": "$state.showConfirmDialog",
  "children": [...]
}
```

#### Flow

```text
content.ui.patch
        ↓
Payload Schema Validation
        ↓
Patch Guard
        ↓
Part Compiler applied
        ↓
workingSpec updated
        ↓
Boundary Validation
        ↓
Promote to renderSpec
        ↓
Vue Renderer
        ↓
VisibilityProvider evaluates $state.showConfirmDialog
        ↓
Display Dialog/Panel when condition is met
```

#### VisibilityProvider Responsibilities

- Determine whether to display Elements based on conditions declared in Spec
- Reference State paths
- Conditional Component display
- Additional UI display based on input values
- Section changes based on selection state
- Internal Loading or Error representation in UI

#### Note

> Visibility only handles screen display. It does not determine business permissions or server execution capability.

## 5. Appropriate Pattern Selection by Popup Type

| Popup Type | Recommended Pattern | Reason |
|------------|---------------------|--------|
| Chat widget/floating UI | A. Chat Widget Open | Requires global state per viewport, shares lifecycle with message stream |
| External site/registered link | B. Registered Link Open | Requires security validation and URL abstraction |
| Internal detail page/modal | C. Product Detail Open | Action-based parameter validation and navigation policy application |
| Conditional display within generative UI | D. Visibility | Spec-based dynamic UI show/hide handling |

---

## 6. Security Checklist

- [ ] UI Components do not directly call `window.open`.
- [ ] Actions are only executed through registered Handlers.
- [ ] External links pass through registered Link IDs and Allowlist.
- [ ] URLs generated by LLM are not used unless validated.
- [ ] `noopener`, `noreferrer` are applied to new window/tab opens.
- [ ] `javascript:`, `data:` schemes are blocked.
- [ ] Visibility is used only for display control, not permission validation.
- [ ] Actions requiring server permissions are re-validated on the server.

## 7. Open Questions

1. **Need for an integrated popup layer**: Should the 4 patterns be integrated into a single `PopupManager`/`DialogStore`, or kept separate as they are now?
2. **A11y**: What is the approach for focus trap, ESC close, and `aria-modal` handling for each open flow?
3. **Back button handling**: How do mobile chat (`mobileOpen`) and Dialog (`visible`) interact with the browser back button?
4. **Animation**: How are open/close transitions handled in each pattern?
5. **z-index/portal**: What is the layer management policy when multiple popups are open simultaneously?
