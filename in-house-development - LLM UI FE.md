# Frontend Structured UI Rendering Layer

## Implementation Target

Implement a Frontend layer that validates the Structured UI Response returned by the Backend
and renders it with registered Vue Components.

User Actions are processed through an Action Dispatcher and State Machine,
and UI Components do not directly call APIs or change state.

# Implementation Purpose

## Dynamic UI Rendering

Based on the Backend's component value,
select and render a pre-registered Vue Component.

## Safe Component Selection

Strings received from the Backend
are not directly used as Vue Component names or Import paths.

Only values registered in the Component Registry are rendered.

## Separation of UI and Business Logic

UI Components are responsible only for the following:

- Data display
- User input display
- Click Event emission
- Input Event emission
- Loading state display

API calls and State changes are handled by a separate layer.

# Overall Processing Flow

## Chat Response Processing

Receive API Response

→ AES decryption

→ JSON Parse

→ Check Contract Version

→ Runtime Schema validation

→ Response Normalize

→ Store in Message Store

→ Component Registry lookup

→ Dynamic Component rendering

## User Action Processing

User button selection

→ UI Component emits Event

→ Response Renderer receives Event

→ Pass to Action Dispatcher

→ Action Registry lookup

→ Action Payload validation

→ State Machine Guard check

→ Handler execution

→ State or Message Store change

→ API call if needed

# Frontend Layer Composition

## Response Parser

Converts the decrypted response into a JSON Object.

## Response Validator

Validates the Contract and data structure of the response.

## Response Normalizer

Normalizes missing default values and previous Contract Versions.

## Message Store

Stores Messages from the user and Assistant.

## Component Registry

Connects component strings to actual Vue Components.

## Response Renderer

Renders the selected Component and forwards Action Events.

## Action Dispatcher

Receives Actions at a central entry point, validates, and executes them.

## Action Registry

Connects Action Types to internal FE Handlers.

## Inquiry State Machine

Manages inquiry composition and transmission states.

## API Client

Handles the following API calls:

- public-key
- chat
- send-message

## Fallback UI

Safely displays invalid responses or rendering errors.

# Message Store

## User Message

## Assistant Message

Assistant Message has the following information:

- id
- role
- response
- component
- props
- actions
- metadata
- createdAt
- status

## Message Status

Allowed states are as follows:

- pending
- completed
- failed

## Excluded Storage Information

The following information is not stored in the Message Store:

- RSA Private Key
- AES Session Key
- Temporary Buffer before decryption
- Original authentication Token
- Unnecessary LLM Provider original response

# Response Runtime Validation

## Validation Timing

Validated after decryption and JSON Parse
before storing in the Message Store.

## Common Validation Items

- Whether response is an Object
- version presence
- component presence
- Whether props is an Object
- Whether actions is an Array
- metadata structure
- Maximum response size

## Component Validation

- Component Registry registration status
- Per-Component Props Schema
- Required Props
- Maximum string length
- Maximum array count
- Allowed Field status

## Action Validation

- Action Registry registration status
- Action Type
- Label
- Style
- Payload structure
- Allowed relationship between Component and Action

## Validation Failure Handling

Invalid responses are not stored in the Message Store
as a general Assistant UI.

Instead, they are replaced with an errorCard response generated by the Frontend.

# Contract Version

## Same Version

Validated and rendered normally.

## Supported Previous Version

Converted to the current version through the Response Normalizer.

## Unsupported Previous Version

Rendering is stopped and errorCard is displayed.

## Future Version

Since the current FE cannot understand the response, it is not rendered.

Only a general error indicating a new version is needed is shown to the user.

# Component Registry

## Registry Purpose

Safely connects the Backend's component string
to the actual Vue Component.

## Registry Registration Items

Initial Components are as follows:

- markdown
- inquiryDraftCard
- inquiryConfirmCard
- inquirySuccessCard
- errorCard

## Registry Policy

- Only explicitly imported Components are registered.
- Unregistered Components are not rendered.
- Unregistered values are replaced with errorCard.
- External strings are not used as Import paths.
- Does not rely on global Component search.
- Component names are managed as part of the API Contract.

## Registry Non-responsibilities

Component Registry does not perform the following:

- API calls
- State changes
- Action execution
- Props processing
- User input validation

# Response Renderer

## Renderer Responsibilities

- Reads the component value from the Response.
- Looks up the actual Component from the Component Registry.
- Passes props to the Component.
- Passes actions to the Component.
- Receives Action Events from the Component.
- Forwards Events to the Action Dispatcher.

## Renderer Non-responsibilities

- Chat API calls
- Inquiry transmission
- Direct State Machine changes
- Action Business Logic execution
- LLM response generation
- Reinterpretation of Props content

## Renderer Fallback

If Component lookup fails or
an error occurs during rendering, errorCard is displayed.

# Action Registry

## Registry Purpose

Connects Action Types delivered from the Backend
to internal Frontend Handlers.

## Registered Actions

- startInquiry
- updateInquiryDraft
- requestInquiryConfirmation
- editInquiry
- sendInquiry
- retryChat
- retryInquiry
- cancelInquiry
- openRegisteredLink

## Registry Policy

- Unregistered Actions are not executed.
- Strings are not directly executed as function names.
- Dynamic code execution is not used.
- Payload is validated before execution.
- State Machine Guard is checked first.
- Execution results are reflected in Message Store or State.

# Inquiry State Machine

## State List

- idle
- editing
- readyToSend
- sending
- sent
- error

## idle State

The state where inquiry has not started.

### Allowed Transitions

- editing

## editing State

The state where the user is entering or editing inquiry content.

### Allowed Transitions

- readyToSend
- idle

## readyToSend State

The state where required information has been validated
and is waiting for user confirmation.

### Allowed Transitions

- editing
- sending

## sending State

The state where the send-message API is being processed.

### Allowed Transitions

- sent
- error

## sent State

The state where the actual inquiry transmission has been completed.

### Allowed Transitions

- idle
- editing

## error State

The state where an error has occurred during inquiry transmission or processing.

### Allowed Transitions

- editing
- sending
- idle

# State Transition Guard

## Validation Items

- Current state
- Requested next state
- Required Draft presence
- Whether request is in progress
- Previous transmission success
- Duplicate Action status

## Block Examples

- Direct transition from idle to sending
- Transition to readyToSend without required values
- Re-executing sendInquiry during sending
- Re-sending the same inquiry in sent state
- Transitioning to sent without resolving the error cause

# Draft State

## Managed Items

- name
- email
- organization
- phone
- message

## Draft Storage Location

Managed in useChatState or a separate Inquiry Store.

## Draft Policy

- Maintain Draft during input
- Maintain Draft even if API error occurs
- Decide whether to initialize after successful transmission
- Default is not to auto-save sensitive Draft to Local Storage
- If refresh restore is needed, separately define storage scope and expiration policy

# requestInquiryConfirmation Processing

## Processing Order

Check current state

→ Validate Draft required values

→ Validate email format

→ Validate string length

→ If errors exist, maintain editing

→ If no errors, transition to readyToSend

→ Display inquiryConfirmCard

# sendInquiry Processing

## Prerequisites

- Current State is readyToSend
- Required Draft validation completed
- Not currently transmitting
- Same inquiry has not already been sent

## Processing Order

Generate idempotencyKey

→ Change State to sending

→ Disable send button

→ Call send-message API

→ Check actual response

## Success Handling

- Change State to sent
- Add inquirySuccessCard
- Store referenceId
- Apply Draft initialization policy

## Failure Handling

- Change State to error
- Maintain Draft
- Display errorCard
- Display retry Action based on retryable

# External Link Processing

## Recommended Structure

The LLM or Backend passes a Link ID instead of a URL.

The Frontend looks up the actual URL
corresponding to the Link ID from the Link Registry.

## Validation Items

- Whether it is a registered Link ID
- Whether it is an allowed Protocol
- Whether it is an allowed Host
- Whether it is a relative or absolute path
- New tab policy
- Whether noopener and noreferrer are applied

## Blocked Items

- javascript Scheme
- data Scheme
- Arbitrary iframe
- Unregistered Domain
- Unvalidated URL generated by LLM

# Markdown Security

## Parser Policy

## Sanitization

When using HTML conversion results,
only results that pass through a Sanitizer are rendered.

## Link Policy

External links apply the following policies:

- Check allowed Protocol
- Check target policy
- Apply rel security attributes
- Block dangerous URLs

# Frontend Completion Conditions

## Component Safety

- Unregistered Components are not rendered.
- Backend strings are not directly used as Component paths.
- All Components are selected through the Registry.

## Action Safety

- Unregistered Actions are not executed.
- All Actions pass through the Dispatcher.
- Action Payload is validated before execution.
- Dynamic code execution is not used.

## State Management

- All inquiry state transitions pass through the State Machine Guard.
- Duplicate requests do not occur during transmission.
- Draft is maintained on error.
- State changes to sent only after actual API success.

## UI Responsibility Separation

- UI Components do not directly call APIs.
- UI Components do not directly change Stores.
- UI Components only emit Events upward.
- Renderer and Dispatcher responsibilities are separated.

## Error Handling

- Invalid responses are replaced with errorCard.
- Contract Version mismatches are handled safely.
- Internal error information is not exposed to the user.
