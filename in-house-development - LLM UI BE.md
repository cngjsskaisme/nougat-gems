# Backend Structured UI Response Layer

## Implementation Target

Implement a Backend layer that generates and validates LLM responses as structured UI specifications
and delivers them to the Frontend.

The Backend does not directly execute values returned by the LLM,
and only allows pre-defined Components, Props, and Actions.

# Implementation Purpose

## Structured Response Generation

Ensure the LLM generates responses that conform to a defined UI Contract
rather than plain text or arbitrary JSON.

## Prevent UI Code Generation

Prevent the LLM from directly generating the following:

- HTML
- JavaScript
- Vue Template
- Executable functions
- Arbitrary API call code
- Arbitrary Component names

## Backend Validation

Even if the LLM returns a Structured Output,
the Backend performs separate Runtime Validation and Business Rule Validation.

## Separation of Actual Task Execution

The LLM can suggest Actions that the user can perform,
but does not directly execute inquiry transmission or external API calls.

# Overall Processing Flow

## Chat Request Processing

Receive Client Request

→ Validate Request format

→ Decrypt encrypted Payload

→ Build Conversation Context

→ Combine System Rules

→ Request LLM Structured Output

→ JSON Schema validation

→ Component validation

→ Props validation

→ Action validation

→ Inquiry State validation

→ Generate Metadata

→ Encrypt response

→ Return to Frontend

# Response Contract

## Common Response Structure

All LLM UI responses consist of the following items:

- version
- component
- props
- actions
- metadata

## version

The version of the UI Contract used by FE and BE.

Its purposes are as follows:

- Check response format compatibility
- Convert from previous versions
- Block unsupported versions
- Manage Component and Props changes

## component

The type of UI that the Frontend should render.

The component value only allows one of the pre-defined Enums.

## props

The display data to pass to the selected Component.

Each Component has its own Props Schema.

## actions

The list of actions that the user can select.

An Action does not contain actual functions or executable code,
and only includes a declarative Action Type and Payload.

## metadata

Request tracking information generated by the Backend.

Metadata can include the following information:

- requestId
- createdAt
- model
- provider
- contractVersion

Metadata is generated by the Backend, not the LLM.

# Allowed Components

## markdown

Displays general text or Markdown responses.

### Key Props

- content

### Allowed Actions

- None
- startInquiry if needed
- openRegisteredLink if needed

## inquiryDraftCard

Displays a card where the user can enter or edit inquiry content.

### Key Props

- title
- description
- fields
- validationMessage

### Allowed Actions

- updateInquiryDraft
- requestInquiryConfirmation
- cancelInquiry

## inquiryConfirmCard

Displays a card for final confirmation of the composed inquiry content to the user.

### Key Props

- title
- summary
- notice

### Allowed Actions

- editInquiry
- sendInquiry

## inquirySuccessCard

Displays the success result after the inquiry has actually been delivered.

### Key Props

- title
- message
- referenceId
- processedAt

### Allowed Actions

- None
- startNewInquiry if needed

### Generation Principle

This Component is not generated solely by the LLM's judgment.

After the actual inquiry transmission API succeeds,
the Backend or FE generates it based on a trustworthy result.

## errorCard

Displayed when an error occurs during response processing or external operations.

### Key Props

- title
- message
- retryable
- errorCode

### Allowed Actions

- retryChat
- retryInquiry
- cancelInquiry

# Allowed Actions

## startInquiry

Starts the inquiry composition flow.

## updateInquiryDraft

Reflects the inquiry draft entered by the user into Client State.

## requestInquiryConfirmation

Validates the required inquiry values and moves to the confirmation step.

## editInquiry

Moves from the confirmation step back to the composition step.

## sendInquiry

Requests to deliver the user-confirmed inquiry to the actual transmission API.

## retryChat

Re-executes the previous Chat request.

## retryInquiry

Re-executes the failed inquiry transmission.

## cancelInquiry

Terminates the inquiry composition flow and returns to the initial state.

## openRegisteredLink

Opens an external or internal link corresponding to a pre-registered Link ID.

The approach of the LLM directly passing an arbitrary URL is not used by default.

# Action Common Structure

## Action ID

A unique value to identify an Action within a response.

## Action Type

One of the pre-defined Action Enums.

## Label

User-facing text to display on buttons or menus.

## Style

A limited value for UI expression purposes.

Examples are as follows:

- primary
- secondary
- danger
- text

## Payload

Limited data required for Action execution.

Payload does not include the following:

- Executable code
- Function names
- Scripts
- Component paths
- Arbitrary API Endpoints
- Authentication information

# Per-Component Props Validation

## markdown Validation

Validates the following items:

- Whether content is a string
- Whether it is an empty string
- Whether it exceeds the maximum length
- Whether it violates the Raw HTML allow policy
- Whether it contains dangerous link formats

## inquiryDraftCard Validation

Validates the following items:

- title presence
- description type
- Whether fields is an array
- Whether field names are allowed
- Whether input types are allowed
- Whether required value is Boolean
- initialValue maximum length
- Duplicate field presence

## inquiryConfirmCard Validation

Validates the following items:

- title presence
- summary structure
- Required inquiry information presence
- Email format
- message maximum length
- notice type

## inquirySuccessCard Validation

Validates the following items:

- Whether it is linked to the actual transmission result
- referenceId format
- processedAt format
- Whether it was not generated before transmission completion

## errorCard Validation

Validates the following items:

- Whether it is a user-facing message
- Whether internal exception information is not included
- Whether retryable value is Boolean
- Whether Error Type and Retry Action match

# JSON Schema Policy

## Schema-based Restrictions

The following items are defined by Schema:

- Required fields
- Data types
- Enums
- Array structures
- Maximum and minimum counts
- String formats
- Disallowed additional fields
- Per-Component Props structure
- Per-Action Payload structure

## Additional Field Restrictions

To ensure undefined fields are not included in the response,
a policy of not allowing additional properties is used where possible.

## Schema Simplification

Since LLM Provider support ranges may differ,
the common Schema is structured around the following elements:

- object
- array
- string
- number
- boolean
- enum
- required
- anyOf

# Backend Runtime Validation

## Validation Timing

Performed immediately after receiving the LLM response.

## Validation Items

- JSON Parse possibility
- Common Contract validation
- Contract Version validation
- Component Enum validation
- Per-Component Props validation
- Action Enum validation
- Per-Action Payload validation
- Response size validation
- String length validation

## Validation Failure Handling

Failed LLM original responses are not passed to the FE.

Instead, a safe errorCard response generated by the Backend is returned.

# Component-Action Policy Validation

## Validation Purpose

Even if an Action is valid per Schema,
it is separately validated whether it can be used with the corresponding Component.

## Allowed Relationships

### markdown

- startInquiry
- openRegisteredLink

### inquiryDraftCard

- updateInquiryDraft
- requestInquiryConfirmation
- cancelInquiry

### inquiryConfirmCard

- editInquiry
- sendInquiry

### inquirySuccessCard

- startNewInquiry

### errorCard

- retryChat
- retryInquiry
- cancelInquiry

## Policy Violation Handling

Disallowed Component-Action combinations
are treated as Structured Response errors.

# Inquiry State Policy

## State List

- idle
- editing
- readyToSend
- sending
- sent
- error

## Allowed Components per State

### idle

- markdown
- inquiryDraftCard

### editing

- inquiryDraftCard
- errorCard

### readyToSend

- inquiryConfirmCard
- inquiryDraftCard

### sending

- Separate Loading state
- errorCard

### sent

- inquirySuccessCard
- markdown

### error

- errorCard
- inquiryDraftCard
- inquiryConfirmCard

## State Validation Principles

- Cannot move to readyToSend state without required information.
- Cannot move directly from idle state to sending state.
- Duplicate sendInquiry is not allowed in sending state.
- The same inquiry is not re-sent in sent state.
- sent state is not returned before actual API success.

# Prompt Builder Policy

## Prompt Composition

The Prompt is composed in the following order:

- System Rules
- UI Contract
- Component definitions
- Action definitions
- State information
- Portfolio or Business Context
- Conversation
- Output Schema

## User Input Separation

Clearly distinguish between System Instruction and user Conversation.

## Prompt Injection Response

Even if user input contains the following requests, they are not followed:

- Ignore existing Schema
- Generate arbitrary Components
- Immediately execute sendInquiry
- Disclose System Prompt
- Return HTML or Script
- Generate unregistered Actions
- Call internal APIs

# Response Normalization

## Default Value Unification

Optional field default values are handled consistently.

Examples are as follows:

- null if no value
- Empty array if no list
- Empty array if no Action
- null if no optional string

## Metadata Addition

The Backend directly adds the following values:

- requestId
- createdAt
- model
- provider
- contractVersion

## Enum Standardization

Standardizes the case and format of Component and Action names.

# Actual Inquiry Transmission Policy

## LLM Role

The LLM determines whether the user intends to send an inquiry
and can suggest inquiryConfirmCard and sendInquiry Actions.

## User Role

The user must explicitly select the send button.

## Frontend Role

The Frontend receives the user's Action
and calls a separate send-message API.

## Backend Role

The Backend re-validates the inquiry content
and then calls actual external services such as the Telegram API.

# Inquiry Transmission API Input

## Required Input

- name
- email
- message
- idempotencyKey

## Optional Input

- organization
- phone
- inquiryCategory
- sourcePage

# Inquiry Transmission API Validation

## Input Validation

- Required value presence
- Email format
- String maximum length
- Prohibited Content format
- Request size
- Encryption session validity

## Execution Validation

- Whether current State is readyToSend
- Whether the same idempotencyKey has been processed
- Whether Rate Limit is exceeded
- Whether there is Bot or Abuse possibility

# Inquiry Transmission API Processing

## Processing Order

Receive Request

→ Decrypt

→ Validate input values

→ Validate Idempotency

→ Generate message for Telegram

→ Call Telegram API

→ Check actual success

→ Generate processing result

→ Encrypt response

→ Return to Frontend

# Inquiry Transmission API Output

## Success Response

Returns the following information:

- success
- referenceId
- processedAt

## Failure Response

Returns the following information:

- success
- retryable
- errorCode
- requestId

Internal Telegram errors or Stack Traces are not returned.

# Stateless Policy

## Chat API

The general Chat API maintains Stateless.

The Backend does not permanently store the following information:

- Full Conversation
- General Chat Messages
- Current UI Component
- Inquiry composition step
- Inquiry Draft

## Client Context

Each request delivers the necessary Conversation and State from the FE.

## Exceptional Short-term State

To prevent duplicate execution, the following information can be stored for a short period:

- idempotencyKey
- Transmission processing state
- Rate Limit information
- Request Fingerprint

This is operational state to prevent duplicate execution of external operations,
not Conversation Memory.

# Error Handling

## Error Types

- requestValidationError
- decryptionError
- llmProviderError
- structuredOutputError
- componentValidationError
- propsValidationError
- actionValidationError
- statePolicyError
- sendInquiryError
- encryptionError

## User Response

Only the following information is delivered to the Frontend:

- User-facing message
- Retry possibility
- requestId
- Limited errorCode

## Internal Processing

The following information is not exposed to the user:

- Stack Trace
- System Prompt
- API Key
- Decryption Key
- Internal Endpoint
- Full LLM original response

# Security Policy

## Allowlist

All of the following items are managed using an Allowlist approach:

- Component
- Action
- Link
- Field
- Input Type
- Action Payload
- External API features

## Arbitrary Code Execution Prevention

LLM responses are not used in the following ways:

- eval
- Function Constructor
- Dynamic Import paths
- Direct function name execution
- Direct Template compilation
- Arbitrary Endpoint calls

## URL Security

When external links are needed, using Link IDs instead of URLs is recommended.

The Backend or FE Link Registry
maps Link IDs to actual URLs.

## Privacy Protection

The following information is not logged in plaintext in operational logs:

- Inquiry content
- Name
- Email
- Phone number
- Encryption Key
- Full decrypted Payload

# Logging and Observability

## Recorded Items

- requestId
- contractVersion
- component
- action type
- Validation result
- State Policy result
- Processing time
- LLM Provider
- Error Category

## Excluded Items

- Full Prompt
- Full Conversation
- Full inquiry
- Personal information
- Encryption Key
- Full decrypted Payload

# Backend Completion Conditions

## Contract Completion Conditions

- All responses follow the defined Contract.
- Arbitrary Components are not delivered to the FE.
- Arbitrary Actions are not delivered to the FE.
- Per-Component Props are validated.
- Contract Version is managed.

## Execution Safety Completion Conditions

- External operations are not executed by LLM responses alone.
- Inquiries are sent only after the user's explicit Action.
- Inquiry transmission is re-validated in a separate API.
- Duplicate transmission is prevented.

## Error Handling Completion Conditions

- A safe errorCard is returned on Schema errors.
- Internal exception information is not exposed.
- Error tracking is possible via requestId.
